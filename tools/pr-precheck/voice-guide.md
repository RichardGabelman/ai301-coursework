## Rules I write by

### Rule: Always use inline code formatting for files and commands

When referencing a file and/or commands, use `` formatting with the entire file name (and path, if possible) and with the entire command + args.

- Wrong: I looked into Component.jsx and found no such error.
- Right: I looked into `Component.jsx` and found no such error.


### Rule: No desperation

No begging to be assigned. No extraneous details about how I've done the same fix/feature before.

- Wrong: Can you please assign me? I've done a similar refactoring on a much larger code base!
- Right: I think it should be *changes*. I should be able to get a PR out soon.


### Rule: No mentioning of my reasons for wanting to contribute

Nobody cares that I'm passionate about X topic. Nobody cares that I'm taking a course that is making me contribute.

- Wrong: I'm taking AI 301 (Open Source AI Capstone!). I am really passionate about Python E2E testing.
- Right: I'd like to take a crack at this issue.

## Things I never post

<!-- A short list. Promises you cannot keep, tones you refuse,
shortcuts you know you reach for when tired. The skill quotes this

- No hard timelines.
- No super confident assertions of the cause of the issue and/or the fix (unless consensus has been reached in either the issue itself or the thread).
- But also, no super insecure tone.
